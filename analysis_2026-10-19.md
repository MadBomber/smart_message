## 1. What the gem is today

- A message is a `Hashie::Dash` subclass with a flat structure: one
  `_sm_header` property plus user properties. Header fields: uuid,
  message_class, published_at, publisher_pid, version, from, to, reply_to,
  serializer.
- `publish` validates (properties, header, version), stamps the header, and
  hands the instance to one or more transports. Success if any transport
  succeeds; `PublishError` only if all fail.
- Each transport owns a serializer and a `Dispatcher`. The dispatcher routes
  by class name, applies from/to/broadcast filters (strings, regexps, arrays),
  checks a per-handler deduplication queue (DDQ), and runs the handler on a
  `Concurrent::CachedThreadPool` inside a BreakerMachines circuit.
- Failures fall to a file-based JSON Lines dead letter queue with replay.
- Handlers: default `Class.process`, `"Class.method"` strings, blocks, procs,
  lambdas. Proc handlers are registered in a class variable keyed by a
  generated id.
- Transports that exist: `MemoryTransport`, `RedisTransport` (pub/sub, channel
  = class name), `FileTransport` (regular files, FIFO, polling subscription,
  partitioned output, async publish queue, rotation), `StdoutTransport`
  (six-line FileTransport subclass).
- Serializer that exists: JSON only.
- Logging: Lumberjack-based logger with text/JSON formats, colorized console,
  file rolling; Null logger when unconfigured.
- Stats: `SimpleStats` exposed as the global constant `SS`, used in the
  publish and route paths.
- Showcase: `examples/city_scenario` (emergency services over Redis).

## 3. Findings

### 3.1 Documented features that do not exist

README, `docs/`, the repo `CLAUDE.md`, and the Rakefile banner all describe a
Redis Queue transport (`:redis_queue`, `#`/`*` pattern routing, consumer
groups, persistent FIFO queues, fluent `where.from.to` API, Async/Fiber
based) and a MessagePack serializer. Neither is in `lib/`.

- Missing: `lib/smart_message/transport/redis_queue_transport.rb`
- Missing: `lib/smart_message/serializer/message_pack.rb`
- Missing docs linked from README: `docs/transports/redis-queue.md`,
  `docs/guides/redis-queue-getting-started.md`, `examples/redis_queue/`
- `lib/smart_message/transport/redis_transport.rb:31` tries to require the
  MessagePack serializer and silently falls back to JSON on `LoadError`.
- `Rakefile:16,20` prints messages about "Redis Queue Transport tests".
- `async` and `async-redis` are runtime dependencies in the gemspec but
  nothing under `lib/` requires them.
- Transport registry registers only `:stdout`, `:memory`, `:redis`
  (`lib/smart_message/transport/registry.rb`). `FileTransport` is not
  registered.

### 3.2 README quick start does not run

- `README.md:144` and `README.md:735` call a class-level `serializer` method
  inside `config do ... end`. No such method exists; `Plugins::ClassMethods`
  only defines `transport` and `logger` (serialization moved into transports).
  Verified: raises `NoMethodError: undefined method 'serializer'`.
- Same lines reference `SmartMessage::Serializer::JSON`; the constant is
  `SmartMessage::Serializer::Json`. Verified: `defined?` returns nil.
- `README.md:765` custom transport example implements
  `publish(message_header, message_payload)`, the old two-argument signature.
  Current `Transport::Base#publish(message)` takes one argument.
- `examples/README.md` lists files such as `01_point_to_point_orders.rb` at
  the examples root; the real files live under `examples/memory/` with
  different numbering.
- Version numbers disagree: gemspec 0.0.17, `mkdocs.yml` `extra.version`
  0.1.11, `docs/index.md` says "documentation is for SmartMessage v0.0.8".

### 3.3 Per-class transport and logger are actually global

`lib/smart_message/plugins.rb:87` and `:124` store the transport and logger in
class variables (`@@transport`, `@@logger`) defined on `SmartMessage::Base`.
Ruby class variables are shared across the whole inheritance hierarchy, so
every message class reads and writes the same slot.

Verified with two classes A and B and two MemoryTransport instances:

```
A.transport t1
B.transport_configured?   # => true  (B was never configured)
B.transport.equal?(t1)    # => true
B.transport t2
A.transport.equal?(t2)    # => true  (A's transport was overwritten)
```

`Addressing` avoided this problem with `@@addressing_registry`, a hash keyed by
class name with inheritance-chain lookup (`lib/smart_message/addressing.rb`).
`Plugins` did not. `@@proc_handlers` in `subscription.rb` is also shared but
is keyed by unique ids so sharing is harmless there.

Impact: the documented "class-level configuration, instance-level override"
model holds for instances but not for classes. The multi-transport and
gateway patterns described in README depend on per-class isolation that does
not exist.

### 3.4 Failure paths have latent bugs

These sit on exactly the paths the README calls "production-grade reliability".

- DLQ signature mismatch. `DeadLetterQueue#enqueue(message, error_info = {})`
  (`lib/smart_message/dead_letter_queue.rb:49`) takes a message object. Four
  callers still pass the old `(header_or_class, payload, opts)` form:
  - `lib/smart_message/transport/base.rb:271` (`handle_publish_fallback`)
  - `lib/smart_message/transport/async_publish_queue.rb:191`
    (`send_to_dead_letter_queue`)
  - `lib/smart_message/dead_letter_queue.rb:144` (`replay_all` re-enqueue)
  - `lib/smart_message/circuit_breaker.rb:176` (`Fallbacks.dead_letter_queue`)
  Verified: `ArgumentError: wrong number of arguments (given 3, expected 1..2)`.
  So a transport circuit trip, async retry exhaustion, or failed replay raises
  instead of recording the message.

- Dead fallback handling. `lib/smart_message/transport/base.rb:70` and
  `lib/smart_message/serializer/base.rb:37,50` do
  `rescue => e; ... if e.is_a?(Hash) && e[:circuit_breaker]`. A rescued
  exception is never a Hash. BreakerMachines returns the fallback hash as the
  value of `wrap`, it does not raise it. `Dispatcher#route` checks the return
  value correctly; Transport and Serializer base classes do not, so their
  `handle_*_fallback` methods are unreachable.

- `Fallbacks.dead_letter_queue` (`circuit_breaker.rb`) expects
  `(exception, header, payload)` but BreakerMachines passes only the
  exception, so `sent_to_dlq` is always false and it falls into the broken
  caller above.

- Circuit DSL re-declared per instance. `self.class.circuit :name do ... end`
  runs inside `initialize` for every Dispatcher, Transport, and Serializer
  (`dispatcher.rb:374`, `transport/base.rb:218,233`, `serializer/base.rb:78`).
  Each new instance redefines the class-level circuit and its storage.

- **Added on re-verification:** the serializer fallback hides failures
  entirely. When encoding raises, `circuit(...).wrap` returns the fallback
  hash, and `Serializer::Base#encode` returns that hash as if it were the
  encoded message. Observed in practice: json 3.x raised on the duplicate keys
  produced by `to_h` (section 7), every JSON encode failed, and the test
  suite stayed green because nothing checked the return type.

- `Dispatcher#initialize` registers an `at_exit` hook per instance
  (`dispatcher.rb:24`). Every transport creates its own dispatcher, so N
  transports means N hooks.

### 3.5 Smaller code issues

- `lib/smart_message/serializer/base.rb:64` default `do_encode` reads
  `message_hash[:_sm_payload]`, a key that no longer exists in the flat
  structure. Only the JSON subclass override is used, so no runtime effect.
- `lib/smart_message/errors.rb:9,13` define `TransportNotConfigured` twice.
  `SerializerNotConfigured` is defined but unused.
- `versioning.rb` stores `@_version` and `@expected_header_version` as class
  instance variables, so `version` does not propagate to subclasses.
- `lib/smart_message.rb` defines a `MilClass` with a `FIXME` that nothing
  references.
- Mixed loading: Zeitwerk is set up, but most files also `require_relative`
  each other.
- `Dispatcher` mutates `@subscribers` without a mutex while pool threads may
  be iterating it.
- `RedisTransport` restarts its subscriber by killing a thread blocked in
  `subscribe` on every new subscription. Works, but crude, and each transport
  instance holds two Redis connections plus a thread.
- `SS` (SimpleStats) is a global constant used in the production publish and
  route paths.

- `dead_letters.jsonl` sits in the repo root. Gitignored, but it is the

## 4. Strategic context

The planning docs tie SmartMessage to BunnyFarm, Agent99, and Lanet. Those
predate the workspace's current agent work (robot_lab, robot_lab-a2a,
simple_a2a, simple_acp). The from/to/reply_to addressing and filter model is
already the right shape for agent-to-agent messaging; the gap is a durable
transport and the correctness issues above.

## 5. Options discussed

1. Make it honest and ship 0.1.0. Remove the Redis Queue and MessagePack
   claims from README, docs, CLAUDE.md, Rakefile, and gemspec; fix the README
   quick start; fix the class-variable sharing (3.3) and the DLQ callers and
   dead fallback branches (3.4); add the missing `minitest/mock` require;
   clean the tracked junk (3.6). Roughly a day.
2. Grow it toward the agent work. Build (or pick) a durable transport so
   robot_lab style agents can use the addressing model over something that
   survives restarts.
3. Trim it. `FileTransport` and its five mixins are about a third of `lib/`.
   If FIFOs and partitioned files have no consumer, removing them makes the
   gem much easier to reason about.

Decision: not yet made as of this date.

## 6. Suggested first fixes, in order

1. `test/stdout_transport_file_inheritance_test.rb`: add
   `require 'minitest/mock'` (restores a green suite). With minitest 6 this
   also needs the `minitest-mock` gem in the gemspec. Only applies once
   `main` is merged; `develop` is already green.
2. `lib/smart_message/plugins.rb`: replace `@@transport` / `@@logger` with a
   per-class registry like `Addressing` uses, with inheritance lookup.
3. `lib/smart_message/dead_letter_queue.rb` and the four callers in 3.4:
   agree on one `enqueue` signature. Simplest is to keep the message-object
   form and give the DLQ a second entry point for raw serialized payloads.
4. `lib/smart_message/transport/base.rb` and `serializer/base.rb`: check the
   return value of `circuit(...).wrap` for the fallback hash instead of
   rescuing. `Serializer::Base#encode` must never return the fallback hash as
   a payload; raise or route to the DLQ instead.
5. Move circuit declarations out of `initialize` to class bodies.
6. README, docs, CLAUDE.md, Rakefile, gemspec: remove the phantom features
   and the unused `async` / `async-redis` dependencies, or build them.
7. `git rm` the `.idea` directory and the `.backup` file; delete stray logs.

## 7. Changes since the analysis (uncommitted, on `develop`)

Made after moving to Ruby 4.1.0-preview1 and running `bundle update --all`.

Environment:

- `.ruby_version` renamed to `.ruby-version` so rbenv selects 4.1.0-preview1.
- `Gemfile.lock` re-locked with bundler 4.1.0.beta2. Bundler 2.7.1 crashes
  on Ruby 4.1 (`Pathname::SEPARATOR_PAT` was removed).

Fixes for breakage from the gem update:

- amazing_print 3.0 crashes on load whenever ActiveSupport is partly loaded.
  `lib/smart_message.rb` now loads `active_support/core_ext/object/try` and
  `active_support/log_subscriber` first (about 6 ms, 13 files).
- `SimpleStats` no longer requires `ap` (a dev-only gem) at load time; it
  uses stdlib `pp`, and `to_s` now returns the text.
- Message `pretty_print` uses amazing_print when installed and falls back
  to stdlib `pp`.
- `Logger::Lumberjack` ported to Lumberjack 2.x: keyword constructor,
  stdlib-style rotation (`roll_by_size`, `roll_by_date`, `date_pattern`
  still honored), one template shared by console and file output, and
  `entry.attributes` instead of the removed `entry.tags`.

Pre-existing bugs fixed along the way:

- `Base#to_h` returned every property twice (nil Symbol keys from
  `Hashie::Dash#to_h` defaults plus String keys from `IndifferentAccess`).
  Same behavior under hashie 5.0.0. Now one Symbol key per property, with
  `to_hash` aliased. Tests added in `test/base_test.rb`.
- Lumberjack JSON format crashed because `json` was never required.
- The log message text leaked into each entry's structured attributes.

Not addressed: every finding in section 3 is still open.
